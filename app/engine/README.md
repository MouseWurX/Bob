# Brain Engine

Brain Engine is a fork of [llama.cpp](https://github.com/ggml-org/llama.cpp), created to give better flexibility when using AI models. It is not an official llama.cpp build.

It is llama.cpp at the tag in `package.json` (`bundledLlamaTag`) with the patches in `engine/patches/` applied in order. [ENGINE-MAP.md](ENGINE-MAP.md) maps where each one hooks into llama.cpp and what to re-check when moving to a newer llama.cpp.

- `0001-expert-mask.patch`: turn a mixture-of-experts brain's experts on or off without reloading it. Engine: `llama_set_expert_mask()`. Server: `GET /expert-mask` and `POST /expert-mask` with `{"keep": null}` (all on), `{"keep": [ids]}` (the same experts in every layer) or `{"keep": [[ids], null, ...]}` (one list per layer, null = all). Each layer keeps at least as many experts as the brain uses for each word. A change clears the cached prompts. It is refused while the server is answering.
- `0002-expert-trace.patch`: report which experts a mixture-of-experts brain picked (`"kind": "experts"`). For a brain with no experts the same request reports groups of neurons instead (`"kind": "neurons"`): each layer's hidden feed-forward neurons, after the activation, are cut into 256 equal runs (`n_expert`; `n_ff` is how many neurons that slices) and the 8 with the highest mean square are listed for every token, busiest first (`n_expert_used`). Server: `"expert_trace": true` on `POST /completion` adds `expert_trace` to the answer: `rows`, one for every token the brain read, in order, each `{"t": the token's text, "e": [[expert ids] for each layer]}`; `n_prompt`, how many of the rows are the prompt (the rest are the answer's own tokens read back, and the experts lit while reading a token are the ones that wrote the next); `last`, the final token written; and `n_layer`, `n_expert`, `n_expert_used`. The last layer is only worked out where an answer is wanted, so its list is empty for the prompt's earlier tokens. The trace is only given to a request that had the brain to itself (ask one at a time); with `stream` it comes with the final piece; `POST /v1/chat/completions` carries it the same way. While a request asks for it the brain is computed step by step, which is slower; nothing changes for requests that don't ask. Engine: `llama_set_eval_callback()`, to set or clear the eval callback of a live context. Bob's Lab uses it for Peek inside's live view and for fNRI. With `"expert_trace_heads": true` as well, any model reports its attention heads instead (`"kind": "heads"`): the attention output of every layer (`kqv_out`) is cut into its `n_head` heads and the busiest (a quarter of them, at most 8) are listed. Neuron and head traces also carry `"a"` on every row: the mean square of the whole node for each layer, which Bob's viewer shows as Floors only.
- `0003-dials.patch`: turn a part of a brain up or down without reloading it. A dial multiplies what one part adds to the stream, which is the same as scaling that part's output weights: one expert of a layer, one attention head of a layer, a layer's whole attention, or a layer's whole feed-forward block. Engine: `llama_set_dials()`. Server: `GET /dials` and `POST /dials` with `{"dials": null}` (everything back to 1) or `{"dials": [{"kind": "expert" | "head" | "attn" | "ffn", "layer": 0, "index": 0, "scale": 0.5}, ...]}` (scale 0 to 8; `index` is the expert or head number). Refused while a slot is busy; prompt caches are cleared on a change. The expert trace reports what the brain does with the dials set. fNRI's Dials use it.
- `0004-rpc-wifi.patch`: card sharing (Bob-Net's "Lend my graphics card") re-sends almost nothing on a reload, which matters most over Wi-Fi. The lent card's server (`ggml-rpc-server -c`) keeps every weight it was sent; upstream only offers it a weight's hash first for weights over 10 MiB, so a mixture-of-experts brain's many 1 to 10 MiB weights (attention, shared experts) went over the network again on every load. Brain Engine offers the hash for every weight over 1 MiB (`GGML_RPC_HASH_MIN` in bytes changes it). Any rpc-server started with `-c` answers a hash of any size, so this works with plain llama.cpp lenders of the same version too. And `ggml-rpc-server --seed FILE.gguf` (more than one may be given) fills that store from a copy of the brain on the lending machine, at disk speed, then exits: each weight over the same size goes in under the name a load asks for, written whole or not at all. It prints `seed: <done>/<total> <file>` lines and exits 0 when every file was seeded. A weight's name is its hash, so a seeded file only ever stands in for the exact same bytes.

- `0005-scut.patch` (experimental): SCUT (Signals and Communications - Universal Transceiver), Bob's own link for card sharing over Wi-Fi. Opt-in on both ends (`GGML_RPC_SCUT=1`); the two sides agree on it in the RPC `HELLO` through the connection-caps field (the same field RDMA uses, so it is never offered when RDMA is), and stay on plain TCP whenever either side doesn't offer it or the UDP path doesn't answer. The RPC commands are unchanged; only how their bytes travel is. The data goes as UDP datagrams with sequence numbers, selective acks (up to 64 ranges) and resends after a few milliseconds measured from the round trip, instead of TCP's 200 to 300 ms timeout after a lost packet at the end of a message. It paces itself with a token bucket at the rate it measures being delivered, under a cap (`GGML_RPC_SCUT_MBPS`, default 300; Bob sets 50, 100 or 300), and backs off when more than 5% is lost in a round trip or the round trip grows, so it doesn't crowd other devices. While words are flowing it sends a 20-byte ping every 25 ms so a handheld's Wi-Fi doesn't doze (`GGML_RPC_SCUT_AWAKE=0` stops that). The UDP side binds the same port number as the server's TCP port; behind a relay, `GGML_RPC_SCUT_PUBLIC_PORT` names the relay's port in the offer (Bob's gate passes UDP on 50052 to the card server's 50053). The TCP connection stays open as the liveness line. SUDDAR (Signal and Uplink Delay Detection and Ranging) is the probe at the start: the client pings the UDP path up to 10 times and times it before both sides switch. Each message's burst of up to 8 datagrams gets one repair datagram (the XOR of the burst; `GGML_RPC_SCUT_FEC=0` turns it off, and it is only sent when the other side says it understands it), so a single lost datagram, usually the last of a small message, is rebuilt at once instead of waiting for a resend. The keep-awake ping is only sent when nothing else has gone out for 25 ms. Each process remembers the pace each lender's line carried, and the next connection to it starts there. Over a simulated Wi-Fi (3 ms, 1% loss) words went from about 9 to about 15 a second; over poor Wi-Fi (5 ms, 3% loss) from about 6 to about 11 (the repair datagrams alone gave about a fifth of that), with byte-identical output.

- `0006-scut-seal.patch`: sealed SCUT packets. With a key, every SCUT datagram both ways (data, acks, repair packets, pings and SUDDAR's probes) is signed and scrambled with ChaCha20-Poly1305 (RFC 8439, in `scut-seal.h`, no outside library), and one that fails the check (changed, made up, sealed with another key, or a replay) is dropped before anything in it is read. The header stays readable but is signed; an 8-byte packet counter is the nonce, so each datagram grows by 24 bytes. Each connection makes one key per direction from the given key and both sides' HELLO nonces (HChaCha20), and each side takes every counter once. The lender's key is `GGML_RPC_SCUT_KEY` (64 hex digits); a borrower with several lenders gives `GGML_RPC_SCUT_KEYS="host:port=key,..."`, matched against the address it connected to, and `host:port=off` means no SCUT with that one. A sealed offer is SCUT version 2 with an `OF_SEAL` flag, so an engine without 0006 never switches to a link it can't read. Both sides sealed, or neither: one with a key and one without stay on TCP. Bob makes the key (src/scut-seal.js): a link key per pair of Bobs made at pairing, turned into a fresh key for each lend. In a test through a fake Wi-Fi that changed 2% of the packets, replayed 2% and made up 2%, all of them were dropped and every byte arrived right (the same test over unsealed SCUT crashed the borrower); speed through that fake Wi-Fi was the same with and without the seal, and one core seals about 3 Gbit/s.

- `0007-expert-trace-stream.patch`: the expert trace as it happens. With `"expert_trace_stream": true` (and `expert_trace` and `stream`), every streamed piece of a reply carries `expert_trace_part`: the trace rows read since the last piece (`from`, `n_prompt`, `rows`, and the same shape fields as the full trace), so Bob's cube lights up with the experts he really uses while he reads and writes, not after. The full trace still comes with the last piece. A piece carries at most 64 rows (a long prompt sends only its end, which is all the cube shows), so the cost stays flat at any context length: measured on a test build, no slower than the trace alone at 32,000 and 128,000 tokens of prompt. A request that doesn't ask gets nothing new.
- `0008-scut-live.patch`: the link log, and SCUT that retunes itself. **The link log:** every `GGML_RPC_STATS` seconds (default 10; `0` turns it off) in which a card-sharing link carried anything, both ends write what it carried, as plain `[link]` lines at the usual log level. The borrowing side (`rpc_dispatcher::work`): which link it is, `SCUT`, or `TCP (not SCUT: the reason)`; messages and bytes each way; how long it waited for answers; and, from one tiny `GET_ALIGNMENT` round trip sent right after an answer (when the other side has nothing left to do), the link's own round trip and so how much of the wait was the link and how much the other card working. A second line lists the six slowest commands. The lending side (`rpc_serve_client`): how long the card worked (graph commands plus the waits in `sync_all_backends`), how long sending answers took, and how long it sat waiting for the next message; once more when the link closes. With SCUT, a `[scut]` line follows: data packets out, sent again, after a timeout, repair packets, packets in, rebuilt, refused (bad seal, replays), bytes on the air, pace against the cap, round trip. On connecting, each side writes `[link] ... connected over ...` with the reason when SCUT was wanted and isn't in use. **Self-tuning** (`OF_TUNE` in the offer, both sides; `GGML_RPC_SCUT_TUNE=0` turns it off): four times a second each side sends a receive report (`T_RXR`: new packets, ones it already had, rebuilt from repairs, out of order, bytes, the longest stall behind a missing packet). Once a second the sender reads the reports next to its own counters and adjusts while the words keep flowing: one repair packet per 8, 4, 2 or 1 data packets (more when packets still had to be sent again, fewer after 20 quiet seconds; messages up to 64 packets get them, where 0005 stopped at 8); the resend timer (up to 1.5 times longer when over 3% of what was sent was resends nobody needed, shorter when timeouts were real losses); the pace (never left below what the other side says arrived); and the keep-awake ping (tried twice as fast for 2 seconds when the round trip, averaged over each second, sat well above its quietest for 3 seconds running; kept only if that brought the average down by three tenths, down to every 4 ms, so one late packet changes nothing). Each change is one `[scut] tuned: ...` line. It also fixes the pace collapsing on a jittery link: a late round trip only counts as a queue when this side was using at least half its pace, and the same now goes for lost packets. An engine without 0008 never sees a report (they're only sent to a side that offered `OF_TUNE`), and repair packets stay in the form 0005 reads. Over pretend Wi-Fi (bench of SCUT alone): a clean link made no changes; with 3% loss or loss in bursts it settled on a repair per 1 or 2 packets and big messages moved at up to twice the pace; words a second stayed within noise, because there a late packet, not a lost one, sets the wait.
- `0011-rpc-read-ahead.patch`: one trip a word instead of several, when a brain is spread over a lent card. After every word the borrowing engine asks the lent card for its results: one `GRAPH_RECOMPUTE`, then a `GET_TENSOR` for each result the next card needs, and each `GET_TENSOR` used to wait for its own answer. In the PC and handheld test that was three trips a word (about 15 ms each on good Wi-Fi), and the borrower spent 90% of its time waiting. The reads after a graph are the same every word, so once the same list has followed a graph twice in a row, the dispatcher sends those reads right behind the next `GRAPH_RECOMPUTE` of that graph, all before waiting for any answer, and hands each answer to the `GET_TENSOR` that asks for it. Nothing changes on the wire (the lent card sees the same commands in the same order), so only the borrowing side needs this build, and a card server from Engine 4 or 5 works with it. A read that wasn't foreseen goes the old way; an answer that turns out not to be wanted is dropped; anything that could change a tensor (a write, a copy, another graph) forgets what was asked ahead, so a read never gets an old value. At most 8 reads of at most 1 MiB each are foreseen. `GGML_RPC_AHEAD=0` turns it off. The link log says how many answers were asked ahead and how many were used. Measured here (`engine/tests/rpc-ahead.cpp`: one graph, three results read back per word, every value checked): over a link with 8 ms round trips 35 words a second became 104; over SCUT through a pretend typical Wi-Fi 17.7 became 30.0, through a weak one 5.0 became 9.6; a tiny brain split over a lent card gave the same answer with it on and off. Sits after `0009` and `0010`, which belong to other work, and touches only `ggml-rpc.cpp`.

The patches change only llama.dll / libllama and llama-server, never ggml or the card backends, with one exception: `0004`, `0005`, `0006` and `0008` change the card-sharing backend (`ggml-rpc.dll` / `libggml-rpc.so`), which is not a card backend and ships in the Brain Engine download. So a Windows Brain Engine is the official CUDA or Vulkan zip for the same tag with `llama.dll`, `llama-server.exe` and the other `llama*`/`mtmd` files swapped for the ones built here. It also carries two tools the official zips leave out (upstream skips them when the card backends load at run time), each built CPU-only as one self-contained file:

- `llama-cvector-generator`: the Lab's "Take out the refusal habit".
- `llama-export-lora`: the Lab's teach step, to fold a taught adapter into a brain file.

And four tools Bob runs beside the server, built from the same tag in the main build (they use the llama files above):

- `llama-bench`: the standard speed test (the Lab's Challenges, "Add the standard speed test").
- `llama-gguf-split`: joins a brain that comes in parts into one file (the Lab's "Bring in a full-size brain"), and splits one for an upload over Hugging Face's 50 GB limit.
- `ggml-rpc-server`: Bob-Net's "Lend my graphics card", so one brain can spread over several of your Bobs' cards. Bob starts it only when a paired Bob asks through the passcode door, binds it to 127.0.0.1 behind a gate that lets in only the asking Bob's address (on the home network when both are on it, else on this machine's Tailscale address; never 0.0.0.0), and stops it when that Bob lets go, after 3 minutes with no word, or when Gaming starts. The RPC server has no passcode of its own, which is why it is never left open.
- `llama-diffusion-cli`: runs diffusion brains (Dream, LLaDA, RND1) in the Lab's Playground. The official llama.cpp downloads don't have it (their builds leave the examples out), so it needs `-DLLAMA_BUILD_EXAMPLES=ON`.

The build turns on `-DGGML_RPC=ON` so the card server exists. Its `ggml-rpc` backend file is Brain Engine's own (patch 0004). The other ggml files are never swapped.

The **Brain Engine** workflow (`.github/workflows/brain-engine.yml`) builds them when `engine/` changes on main or in a pull request that is ready for review, and by hand. Pushes to work branches and draft pull requests build nothing, so a patch that is still being worked on never sends a failed-build e-mail. Check a new or changed patch with your own build first: `bash engine/try-newer.sh` for a move to a newer tag, or apply the patches to a clone of the tag and build the same targets as the workflow (on Windows too when the patch touches code that includes `windows.h`).

## Moving to a newer llama.cpp

`engine/try-newer.sh [TAG]` puts the patches on the tag Bob is on now (one commit each), then replays them on `TAG` (default: the newest `bNNNN`) with git's three-way merge, so a patch whose surrounding lines only moved still goes on. The moved patches land in `try-newer/patches/` with the same names. When one needs a hand, `try-newer/conflict.txt` names it and its files.

Then: copy the moved patches into `engine/patches/`, set `bundledLlamaTag` in `package.json` to the new tag, add one to `bob.brainEngineVersion`, and push. The Brain Engine workflow builds it on Windows and Linux. Publishing the pre-release (`brain-engine-<brainEngineVersion>b<llama.cpp build>`, by hand with "publish" ticked), the PC test, and a Bob release that sets `bob.brainEngine` (tag and both sha256 prints) come after, so Bob's built-in llama.cpp and Brain Engine always move together.

**Version numbers.** Brain Engine has its own: every new build (new patches, or a newer llama.cpp underneath) gets the next `bob.brainEngineVersion`. From build 5 a build is named **N1bN2**: that number, a `b`, then the llama.cpp build it's made on, so build 5 on llama.cpp b12282 is **Brain Engine 5b12282**, its release `brain-engine-5b12282` and its files `brain-engine-5b12282-win-x64.zip` and `-linux-x64.tar.gz` (the workflow makes the name from `brainEngineVersion` and `bundledLlamaTag`). Always add one to `brainEngineVersion` before publishing, so a rebuild never replaces files a released Bob is pinned to. Older builds keep their names: 3 and 4 are `brain-engine-v3`/`brain-engine-v4` ("version 4, built on llama.cpp b12282"), and builds 1 and 2 are named after their llama.cpp tag (`brain-engine-b12032`, `brain-engine-b12282`). Bob reads all three (`public/engine-name.js`). Settings, Engines and the logbook name the build from the installed folder's marker, and when a brain loads Bob checks the running engine's `/props` `build_info` against the llama.cpp number in the name, and notes it in the logbook if they differ.

The **Brain Engine newer llama.cpp check** (`.github/workflows/brain-engine-newer.yml`) runs this every Monday and builds the result on Linux. When the patches go on and it builds, it opens one issue, "New Brain Engine ready on llama.cpp bNNNN - rebuild it?", with the moved patches as a download; later weeks edit that same issue. It never changes Bob, and the run stays green whatever it finds.

llama.cpp changes its card-sharing protocol now and then (b12282 is version 9; b12032 was 8). A lender and a borrower must speak the same version, so every Bob that shares cards needs the same Brain Engine.
