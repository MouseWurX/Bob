# Brain Engine

Brain Engine is a fork of [llama.cpp](https://github.com/ggml-org/llama.cpp), created to give better flexibility when using AI models. It is not an official llama.cpp build.

It is llama.cpp at the tag in `package.json` (`bundledLlamaTag`) with the patches in `engine/patches/` applied in order. Most patches change only llama and the server, but some change ggml itself, including the CUDA card code (0026, 0038, 0039, 0042, 0044, 0045, 0046), the Vulkan card code (0135, 0136), the CPU backend (0020, 0026, 0038, 0039, 0040, 0042, 0045, 0046, 0136), the scheduler (0017, 0029, 0033), the back-end door every support question goes through (0045) and card sharing (the rpc patches, and the one-line or few-line changes of 0042 and 0045). A build with those carries its own ggml files. [ENGINE-MAP.md](ENGINE-MAP.md) maps where each one hooks into llama.cpp and what to re-check when moving to a newer llama.cpp.

- `0001-expert-mask.patch`: turn a mixture-of-experts brain's experts on or off without reloading it. Engine: `llama_set_expert_mask()`. Server: `GET /expert-mask` and `POST /expert-mask` with `{"keep": null}` (all on), `{"keep": [ids]}` (the same experts in every layer) or `{"keep": [[ids], null, ...]}` (one list per layer, null = all). Each layer keeps at least as many experts as the brain uses for each word. A change clears the cached prompts. It is refused while the server is answering.
- `0002-expert-trace.patch`: report which experts a mixture-of-experts brain picked (`"kind": "experts"`). For a brain with no experts the same request reports groups of neurons instead (`"kind": "neurons"`): each layer's hidden feed-forward neurons, after the activation, are cut into 256 equal runs (`n_expert`; `n_ff` is how many neurons that slices) and the 8 with the highest mean square are listed for every token, busiest first (`n_expert_used`). Server: `"expert_trace": true` on `POST /completion` adds `expert_trace` to the answer: `rows`, one for every token the brain read, in order, each `{"t": the token's text, "e": [[expert ids] for each layer]}`; `n_prompt`, how many of the rows are the prompt (the rest are the answer's own tokens read back, and the experts lit while reading a token are the ones that wrote the next); `last`, the final token written; and `n_layer`, `n_expert`, `n_expert_used`. The last layer is only worked out where an answer is wanted, so its list is empty for the prompt's earlier tokens. The trace is only given to a request that had the brain to itself (ask one at a time); with `stream` it comes with the final piece; `POST /v1/chat/completions` carries it the same way. While a request asks for it the brain is computed step by step, which is slower; nothing changes for requests that don't ask. Engine: `llama_set_eval_callback()`, to set or clear the eval callback of a live context. Bob's Lab uses it for Peek inside's live view and for fNRI. With `"expert_trace_heads": true` as well, any model reports its attention heads instead (`"kind": "heads"`): the attention output of every layer (`kqv_out`) is cut into its `n_head` heads and the busiest (a quarter of them, at most 8) are listed. Neuron and head traces also carry `"a"` on every row: the mean square of the whole node for each layer, which Bob's viewer shows as Floors only.
- `0003-dials.patch`: turn a part of a brain up or down without reloading it. A dial multiplies what one part adds to the stream, which is the same as scaling that part's output weights: one expert of a layer, one attention head of a layer, a layer's whole attention, or a layer's whole feed-forward block. Engine: `llama_set_dials()`. Server: `GET /dials` and `POST /dials` with `{"dials": null}` (everything back to 1) or `{"dials": [{"kind": "expert" | "head" | "attn" | "ffn", "layer": 0, "index": 0, "scale": 0.5}, ...]}` (scale 0 to 8; `index` is the expert or head number). Refused while a slot is busy; prompt caches are cleared on a change. The expert trace reports what the brain does with the dials set. fNRI's Dials use it.
- `0004-rpc-wifi.patch`: card sharing (Bob-Net's "Lend my graphics card") re-sends almost nothing on a reload, which matters most over Wi-Fi. The lent card's server (`ggml-rpc-server -c`) keeps every weight it was sent; upstream only offers it a weight's hash first for weights over 10 MiB, so a mixture-of-experts brain's many 1 to 10 MiB weights (attention, shared experts) went over the network again on every load. Brain Engine offers the hash for every weight over 1 MiB (`GGML_RPC_HASH_MIN` in bytes changes it). Any rpc-server started with `-c` answers a hash of any size, so this works with plain llama.cpp lenders of the same version too. And `ggml-rpc-server --seed FILE.gguf` (more than one may be given) fills that store from a copy of the brain on the lending machine, at disk speed, then exits: each weight over the same size goes in under the name a load asks for, written whole or not at all. It prints `seed: <done>/<total> <file>` lines and exits 0 when every file was seeded. A weight's name is its hash, so a seeded file only ever stands in for the exact same bytes.

- `0005-scut.patch` (experimental): SCUT (Signals and Communications - Universal Transceiver), Bob's own link for card sharing over Wi-Fi. Opt-in on both ends (`GGML_RPC_SCUT=1`); the two sides agree on it in the RPC `HELLO` through the connection-caps field (the same field RDMA uses, so it is never offered when RDMA is), and stay on plain TCP whenever either side doesn't offer it or the UDP path doesn't answer. The RPC commands are unchanged; only how their bytes travel is. The data goes as UDP datagrams with sequence numbers, selective acks (up to 64 ranges) and resends after a few milliseconds measured from the round trip, instead of TCP's 200 to 300 ms timeout after a lost packet at the end of a message. It paces itself with a token bucket at the rate it measures being delivered, under a cap (`GGML_RPC_SCUT_MBPS`, default 300; Bob sets 50, 100 or 300), and backs off when more than 5% is lost in a round trip or the round trip grows, so it doesn't crowd other devices. While words are flowing it sends a 20-byte ping every 25 ms so a handheld's Wi-Fi doesn't doze (`GGML_RPC_SCUT_AWAKE=0` stops that). The UDP side binds the same port number as the server's TCP port; behind a relay, `GGML_RPC_SCUT_PUBLIC_PORT` names the relay's port in the offer (Bob's gate passes UDP on 50052 to the card server's 50053). The TCP connection stays open as the liveness line. SUDDAR (Signal and Uplink Delay Detection and Ranging) is the probe at the start: the client pings the UDP path up to 10 times and times it before both sides switch. Each message's burst of up to 8 datagrams gets one repair datagram (the XOR of the burst; `GGML_RPC_SCUT_FEC=0` turns it off, and it is only sent when the other side says it understands it), so a single lost datagram, usually the last of a small message, is rebuilt at once instead of waiting for a resend. The keep-awake ping is only sent when nothing else has gone out for 25 ms. Each process remembers the pace each lender's line carried, and the next connection to it starts there. Over a simulated Wi-Fi (3 ms, 1% loss) words went from about 9 to about 15 a second; over poor Wi-Fi (5 ms, 3% loss) from about 6 to about 11 (the repair datagrams alone gave about a fifth of that), with byte-identical output.

- `0006-scut-seal.patch`: sealed SCUT packets. With a key, every SCUT datagram both ways (data, acks, repair packets, pings and SUDDAR's probes) is signed and scrambled with ChaCha20-Poly1305 (RFC 8439, in `scut-seal.h`, no outside library), and one that fails the check (changed, made up, sealed with another key, or a replay) is dropped before anything in it is read. The header stays readable but is signed; an 8-byte packet counter is the nonce, so each datagram grows by 24 bytes. Each connection makes one key per direction from the given key and both sides' HELLO nonces (HChaCha20), and each side takes every counter once. The lender's key is `GGML_RPC_SCUT_KEY` (64 hex digits); a borrower with several lenders gives `GGML_RPC_SCUT_KEYS="host:port=key,..."`, matched against the address it connected to, and `host:port=off` means no SCUT with that one. A sealed offer is SCUT version 2 with an `OF_SEAL` flag, so an engine without 0006 never switches to a link it can't read. Both sides sealed, or neither: one with a key and one without stay on TCP. Bob makes the key (src/scut-seal.js): a link key per pair of Bobs made at pairing, turned into a fresh key for each lend. In a test through a fake Wi-Fi that changed 2% of the packets, replayed 2% and made up 2%, all of them were dropped and every byte arrived right (the same test over unsealed SCUT crashed the borrower); speed through that fake Wi-Fi was the same with and without the seal, and one core seals about 3 Gbit/s.

- `0007-expert-trace-stream.patch`: the expert trace as it happens. With `"expert_trace_stream": true` (and `expert_trace` and `stream`), every streamed piece of a reply carries `expert_trace_part`: the trace rows read since the last piece (`from`, `n_prompt`, `rows`, and the same shape fields as the full trace), so Bob's cube lights up with the experts he really uses while he reads and writes, not after. The full trace still comes with the last piece. A piece carries at most 64 rows (a long prompt sends only its end, which is all the cube shows), so the cost stays flat at any context length: measured on a test build, no slower than the trace alone at 32,000 and 128,000 tokens of prompt. A request that doesn't ask gets nothing new.
- `0008-scut-live.patch`: the link log, and SCUT that retunes itself. **The link log:** every `GGML_RPC_STATS` seconds (default 10; `0` turns it off) in which a card-sharing link carried anything, both ends write what it carried, as plain `[link]` lines at the usual log level. The borrowing side (`rpc_dispatcher::work`): which link it is, `SCUT`, or `TCP (not SCUT: the reason)`; messages and bytes each way; how long it waited for answers; and, from one tiny `GET_ALIGNMENT` round trip sent right after an answer (when the other side has nothing left to do), the link's own round trip and so how much of the wait was the link and how much the other card working. A second line lists the six slowest commands. The lending side (`rpc_serve_client`): how long the card worked (graph commands plus the waits in `sync_all_backends`), how long sending answers took, and how long it sat waiting for the next message; once more when the link closes. With SCUT, a `[scut]` line follows: data packets out, sent again, after a timeout, repair packets, packets in, rebuilt, refused (bad seal, replays), bytes on the air, pace against the cap, round trip. On connecting, each side writes `[link] ... connected over ...` with the reason when SCUT was wanted and isn't in use. **Self-tuning** (`OF_TUNE` in the offer, both sides; `GGML_RPC_SCUT_TUNE=0` turns it off): four times a second each side sends a receive report (`T_RXR`: new packets, ones it already had, rebuilt from repairs, out of order, bytes, the longest stall behind a missing packet). Once a second the sender reads the reports next to its own counters and adjusts while the words keep flowing: one repair packet per 8, 4, 2 or 1 data packets (more when packets still had to be sent again, fewer after 20 quiet seconds; messages up to 64 packets get them, where 0005 stopped at 8); the resend timer (up to 1.5 times longer when over 3% of what was sent was resends nobody needed, shorter when timeouts were real losses); the pace (never left below what the other side says arrived); and the keep-awake ping (tried twice as fast for 2 seconds when the round trip, averaged over each second, sat well above its quietest for 3 seconds running; kept only if that brought the average down by three tenths, down to every 4 ms, so one late packet changes nothing). Each change is one `[scut] tuned: ...` line. It also fixes the pace collapsing on a jittery link: a late round trip only counts as a queue when this side was using at least half its pace, and the same now goes for lost packets. An engine without 0008 never sees a report (they're only sent to a side that offered `OF_TUNE`), and repair packets stay in the form 0005 reads. Over pretend Wi-Fi (bench of SCUT alone): a clean link made no changes; with 3% loss or loss in bursts it settled on a repair per 1 or 2 packets and big messages moved at up to twice the pace; words a second stayed within noise, because there a late packet, not a lost one, sets the wait.
- `0009-expert-mass.patch`: with `"expert_trace": true`, a mixture-of-experts trace also carries `experts` (how many the brain has) and `layers`: for every layer, how many times each expert was picked over the request's tokens (`null` for a layer with no router). With `"expert_trace_mass": true` as well, it carries `mass`, laid out the same: for every layer and expert, the sum over its picks of the router's weight times the size (L2 norm) of what the expert wrote. It is the norm of each layer's weighted expert output (`ffn_moe_weighted`, which is w · f(x)) taken once and never multiplied by w again, so it equals w · ‖f(x)‖ (the weights are never negative). w is the weight the brain really uses: after its own renormalising over the picked experts and scaling (for Qwen MoE, renormalised over the top k), not the raw softmax over all experts. This is the REAP numerator, the same number the Forge's `pod/reap.py` measures on a rented card, and `experts`/`layers`/`mass` is the Forge's counts file shape, so `pod/keep.py` (`--by counts`, `mass` or `reap`, where REAP = mass / picks) reads a trace as it is. The numbers reflect the brain as it runs, dials included. Only the tokens the request computed count: send `"cache_prompt": false` so the whole prompt is read, and the last layer only sees the tokens that wrote a word (as in the rows). A brain that weighs what goes into its experts instead (llama4) gets `"mass": null` and `mass_why`. Asking for mass copies every layer's expert outputs, so it is slower than a plain trace; requests that don't ask are unchanged.
- `0010-expert-trace-once.patch`: the expert trace without stopping the card at every layer. With 0002 alone, a request with `expert_trace` made the engine stop after every layer's expert picks, wait for the card, and copy them out: 40 to 48 stops per word, which cost Riker about a fifth of his word speed on a 5070 Ti (122.7 to 99.2 words a second, and a quarter on a small brain without experts). Now each layer's picks (`ffn_moe_topk-<layer>` and the sort it views) are kept on the card until the step is done (`llama_set_keep_expert_ids()`, which marks them as graph outputs and lays out the scheduler's memory again), and the trace stops once, at the last layer with experts, and fetches every layer's picks together with one wait (`llama_get_tensors()`). The first step of each request still stops at every layer, to learn which layer is the last. The trace it gives is the same, row for row (checked on a test build, short and long prompts, in pieces and whole). Neuron and head traces (brains without experts, `expert_trace_heads`) and a trace with `expert_trace_mass` (0009) still stop at every layer. While the picks are kept the scheduler's working memory grows by the picks of one step: each layer's sort, `n_expert` × `n_ubatch` × 4 bytes (about 20 MB for Riker at 512).
- `0011-rpc-read-ahead.patch`: one trip a word instead of several, when a brain is spread over a lent card. After every word the borrowing engine asks the lent card for its results: one `GRAPH_RECOMPUTE`, then a `GET_TENSOR` for each result the next card needs, and each `GET_TENSOR` used to wait for its own answer. In the PC and handheld test that was three trips a word (about 15 ms each on good Wi-Fi), and the borrower spent 90% of its time waiting. The reads after a graph are the same every word, so once the same list has followed a graph twice in a row, the dispatcher sends those reads right behind the next `GRAPH_RECOMPUTE` of that graph, all before waiting for any answer, and hands each answer to the `GET_TENSOR` that asks for it. Nothing changes on the wire (the lent card sees the same commands in the same order), so only the borrowing side needs this build, and a card server from Engine 4 or 5 works with it. A read that wasn't foreseen goes the old way; an answer that turns out not to be wanted is dropped; anything that could change a tensor (a write, a copy, another graph) forgets what was asked ahead, so a read never gets an old value. At most 8 reads of at most 1 MiB each are foreseen. `GGML_RPC_AHEAD=0` turns it off. The link log says how many answers were asked ahead and how many were used. Measured here (`engine/tests/rpc-ahead.cpp`: one graph, three results read back per word, every value checked): over a link with 8 ms round trips 35 words a second became 104; over SCUT through a pretend typical Wi-Fi 17.7 became 30.0, through a weak one 5.0 became 9.6; a tiny brain split over a lent card gave the same answer with it on and off. Sits after `0009` and `0010`, which belong to other work, and touches only `ggml-rpc.cpp`.
- `0012-load-progress.patch`: says how far a brain has loaded. llama-server already follows the load (about one sample every 200 ms) but only tells a router about it, and prints nothing otherwise. With this patch a server not run by a router prints `load_progress: text_model <percent>` lines while it loads, from 0 to 100. Bob reads them (`loadDots()` in `src/llamacpp.js`) so the brain cube fills like a progress bar. Nothing changes for a server run by a router, and nothing is sent to clients. Touches only `tools/server/server.cpp`.
- `0013-experts-per-word.patch`: change how many experts a mixture-of-experts brain asks for each word without reloading it (gpt-oss asks 4, Qwen3 MoE 8). Engine: `llama_set_expert_used(ctx, used, n)` (one count per layer, 0 = the brain's own; `NULL` puts every layer back), `llama_get_expert_used(ctx, il)` and `llama_model_n_expert_used_layer(model, il)`. Server: `GET /experts-per-word` (`n_layer`, `n_expert`, `n_expert_used`, `own` and `used` per layer, `live`) and `POST /experts-per-word` with `{"used": null}` (the brain's own), `{"used": 6}` (6 in every layer) or `{"used": [6, null, 4, ...]}` (one per layer, null or 0 = own). The count replaces the brain's own in `build_moe_ffn` for that layer (never in warmup, or for a layer handed its picks by another), the graph is rebuilt and the scheduler's working memory laid out again before the call returns, so a count that doesn't fit in memory is refused there with the old counts kept, never in the next word. Refused while a slot is busy; prompt caches are cleared on a change; refused for a brain whose layers share one router (granite-switch), for more than the expert mask keeps in a layer (and a mask narrower than the count is refused too), and for more than the brain's own count while a MoE cache is on (its slots are sized for the own count). The expert trace (0002, 0007, 0009, 0010) now follows a different count in each layer: a row's `e` lists each layer's own picks, and `n_expert_used` is the most any layer picked. Measured here (`engine/tests/experts-per-word.py`, a tiny made-up brain with 16 experts and 2 per word): switching 2, 3, 2, 4 live gives the same words and odds as starting the engine with `--override-kv qwen3moe.expert_used_count=int:N` at each count; one count per layer shows in the trace layer by layer. Speed, estimated from the shape (writing a word mostly reads weights: the attention, the output and the picked experts, so time follows the share that is experts): on gpt-oss-120b against its own 4 with most experts in RAM, where they are 85 to 90% of the time, 3 is about 20 to 30% faster, 5 about 15 to 20% slower, 6 about 30% slower; with the whole brain on the card, where MXFP4 experts are under half the bytes read, about half those changes. Memory doesn't change. Not measured on a real brain yet. Off unless asked for: nothing changes for a brain no one sends a count for. Applies after `0001` to `0011` with or without `0012`.
- `0016-moe-cache-ranking.patch`: fill llama.cpp's own expert cache (`--moe-cache-mib`) at load, from a ranking of the experts, so the busiest experts sit on the card from the first word instead of being learned during the first minutes. **`LLAMA_MOE_CACHE_RANKING` holds the PATH of a ranking file** (not a number). The file is text: `bob-moe-ranking 2 <fingerprint> <stamp>`, then one `<layer> <expert> <count>` line per expert; Bob writes it from the calibration counts (`src/hot-experts.js`). Each group of the cache takes its busiest experts (ties by layer and expert, so one file always gives one placement) until its slots are full, and copies them to the card once. At load the engine always prints `MoE cache brain fingerprint = <16 hex>` (FNV-1a over every expert tensor's type, shape and first and last bytes, so the same brain file gives the same number at any cache size or placement). A ranking that is missing, malformed, made on another brain (fingerprint), or naming a layer or expert this brain doesn't have is refused before any slot is touched, with a warning starting `!!! MoE cache ranking NOT USED`, and the cache fills the stock way. With `--moe-cache-cpu-share 1` a missed expert is worked out on the processor instead of copied over, so while writing one word at a time nothing moves. Small batches (2 to 32 tokens, such as Turbo's checks) can still copy a few in when the cache's spare slots run out. **Prompt reading never benefits:** batches over 32 tokens skip the cache, so a ranking can't make prompt reading or the first word of a long prompt faster. `LLAMA_MOE_CACHE_LOG_EVERY=N` (off unless set) prints the hit, miss and MB-copied totals every N cache updates, so a test can read them while the server runs (on Windows a stopped server never prints its totals). **These are info lines, and llama-server shows the engine's info lines only at `-lv 4` or above** (it files them one level under its default of 3; warnings, such as a refused ranking, show at any level). Bob, Calibrate, `hot-rank.mjs` and the speed-test runner pass `-lv 4`; level 4 is not debug (5), so it adds no per-word lines. Found on the PC Nov 16. **Known problem in Brain Engine 9:** while the cache is on (`--moe-cache-mib`), the expert trace (0002) comes back empty, on both `/completion` and `/v1/chat/completions` (seen on the PC Nov 16; cause not found yet, it needs a graphics card to look into). Until it is fixed, Calibrate and `hot-rank.mjs` load twice: once with the cache for the fingerprint, once without it to count the picks. The live cube shows no real experts while Hot experts is on. Only `src/llama-moe-cache.cpp` changes. No graph, ggml or card backend code.
- `0017-moe-cache-split-guard.patch`: a fix, always on. The expert cache works out its copies from the experts each layer picked, so those picks must be done in an earlier piece of the graph than the cache lookup. llama.cpp starts that new piece only when the current one already reads something from the other side; when it read nothing yet the engine stopped with "the experts of layer N are selected in the same split as their MoE cache lookup". This happened on the PC with the chat memory split (0036) on, whose processor attention changes where the pieces fall. The cache's slot maps now carry a flag (`GGML_TENSOR_FLAG_SPLIT`) and their lookup always starts a new piece. Where the run worked before, nothing changes. Touches `ggml.h`, `ggml-backend.cpp` (the scheduler) and `src/llama-moe-cache.cpp`; no card backend code. Numbered 0017 because it needs nothing from 0018 on.
- `0018-expert-trace-every.patch`: the live expert trace (0007) sent every N written words instead of every word. A request with `"expert_trace_every": N` (1 to 64, default 1) gets a piece with the first word and then with every Nth; the rows in between ride in the next piece, and the full trace still comes at the end. With no piece there's no wait for the card, so the engine stops once every N words instead of every word. Checked here (`engine/tests/trace-every.py`, the tiny made-up brain): at N = 4 there were 7 pieces for 24 words instead of 24, with the same rows in the same order and the same full trace. Speed not measured yet. Numbered after 0015 (prompt odds) and 0016; applies on top of them. Touches only `tools/server`.
- `0019-expert-prefetch.patch`: copy the next layer's experts to the card while this layer works, when reading a long prompt with part of a mixture-of-experts brain in RAM. Off unless `LLAMA_PREFETCH_EXPERTS=1`. Without it, each layer's experts are copied to the card right before that layer on the card's own stream, so the card waits for every copy. With it, once a layer's expert tensor has gone over with at least half its experts in use, the same tensor of the next layer in RAM is copied whole into a staging buffer on a second stream of the same card; when the scheduler asks for it, the card waits for that copy on the card (not the processor) and moves it into place inside its own memory. Costs about one layer of experts more on the card (one staging buffer per kind of expert tensor, allocated at first use); with no room, or no second stream or events, it turns itself off with a `!!! expert prefetch NOT USED` warning. One-word writing is untouched. Prints how many tensors were copied ahead and used when the engine stops. Works best when the brain's RAM part is pinned (loaded whole, not mapped); with a mapped file the copy may hold up the processor. Sits in the copy callback llama already gives the scheduler (`src/llama-context.cpp`); no ggml, scheduler or card backend code changes. Compiles here (CPU); it can only run on a card, so it is untested until the PC test. Not measured.
- `0020-expert-tiers.patch`: hot, warm and cold experts, for brains bigger than the RAM. **Hot** is the card (the expert cache, 0016). **Warm** (`LLAMA_EXPERT_WARM_MIB=N`, off unless set): the busiest experts that sit in RAM are pinned there, up to N MiB, so the operating system never drops them back to the disk; the order comes from the same ranking file as 0016 (`LLAMA_EXPERT_WARM_RANKING`, or `LLAMA_MOE_CACHE_RANKING`), checked the same way, and a wrong or broken one pins nothing with a `!!! warm experts NOT PINNED` warning. **Cold** (`LLAMA_EXPERT_READ_WHOLE=1`, off unless set): when the router picks an expert that hasn't been used in the last 64 products of that tensor (`LLAMA_EXPERT_READ_WINDOW`), the engine asks the operating system for that whole expert at once (`PrefetchVirtualMemory` on Windows 8 or newer, `madvise` on Linux, Mac and Android) instead of letting it come in a few pages at a time; it works the same whether the expert is in the brain file or in the page file. Neither changes a number, so the words are identical. Checked here (`engine/tests/expert-tiers.py`, the tiny made-up brain, 17 checks, including that the cube's expert trace still comes back). **Speed not measured:** it can only help when the brain doesn't fit in RAM (GPT-OSS 120B on the PC). Pinning has system limits: on Linux and Android `ulimit -l` is often tiny, so the warm tier stops early with a warning; on Windows it raises the working set as llama.cpp's own mlock does. The only patch in the CPU backend.
- `0021-expert-trace-kept.patch`: the cube's expert trace without slowing Bob or changing his words. Until now the trace read each layer's picks through an eval callback, and 0010 marked the router's sorted list as a graph output so all layers could be read at once. On the card both cost: the PC test measured the trace at -11% writing with different (but steady) words, and the cube check showed the callback alone changes the words too (G2, -27%). Now each layer's picks are copied, right after the router's fused kernel, into its place in one small tensor per device (`[k_max, layers, n_ubatch]` int32, token-major, about 640 KB for 40 layers at reading step 512); after each micro-batch the context queues one copy of the block those tokens used (1.3 KB for one written word) to pinned host memory on the same stream, so it lands before the next micro-batch writes it again, and sorts it into layers when the trace is read. On the PC Brain Engine 11 (one copy per layer per word, into ordinary memory) kept the words identical but cost 4% at Normal; this is the change for that, not measured yet. No eval callback, no `ggml_set_output`, so the fused top-k kernel and CUDA graphs stay on. A layer whose experts go through the hot-experts cache's slots (one word at a time, up to 32 words) gets no copy: the cache already reads that layer's picks to the host for its lookup, and hands them over (`llama_moe_cache::set_ids_sink`). On the PC the first build crashed on the first written word with the cache and the trace both on (`GGML_ASSERT(sel->op == GGML_OP_RESHAPE)` in the cache): the copy moved the graph's splits around the cache's lookup. New: `llama_get_kept_expert_ids(ctx, il, &ids, &k)` and `llama_clear_kept_expert_ids(ctx)`. The expert mass (0009) and the neuron and head traces keep the callback. Checked here (`engine/tests/trace-kept.py`, the tiny made-up brain on the processor, 16 checks): same words and odds with the trace on and off, the picks identical to the callback's token for token and layer for layer, in one micro-batch and in micro-batches of 16; the 0013 per-layer counts (3, 2, 4, 2) still trace. **Speed and the words on the card not measured yet:** that's the cube check on the PC once Brain Engine 10 is built.
- `0022-lend-cache-to-reading.patch`: read long prompts in a bigger step without giving up the hot-experts cache for writing. Reading in steps of more than 32 words never uses the cache (it would throw out the experts writing needs), so during a long read its card memory sits idle, while a bigger reading step wants exactly that memory. With `LLAMA_MOE_CACHE_LEND=N` (off unless set; N over 32 and under `-ub`; `-b` at least `-ub`), a request of up to N words reads with the cache in place, in working memory laid out for N words; a longer one first frees the cache's card memory, lays the working memory out again for the full `-ub` step and reads in it; the first write of 32 words or fewer (or a short tail of the prompt) frees that working memory, allocates the cache again, uploads the same experts into the same slots, and lays the working memory out for N again. So the cache comes back exactly as it was, and the words are the same as with the cache never lent at the same reading steps. Example for the 16 GB card: `-ub 6144 -b 6144`, cache 4 GB, `LLAMA_MOE_CACHE_LEND=4096` (read short prompts like X4c, long ones like the 6144 step). The log says each switch and how long it took (`MoE cache lent in ... ms`, `cache back from prompt reading: ... experts (... MiB) uploaded again in ... ms`). The upload back from RAM is the cost: estimated 0.2 to 0.6 s for 4 GB, paid once per long prompt, before the first word. On the PC (Brain Engine 13, Qwen 35B, 16 GB card, 32K prompt): no failures, the same words as step 6144, writing 92.8 words a second (step 6144 with a 3.5 GB cache: 88.4), lent in 78 to 99 ms and back in 274 to 286 ms (4,091 MiB), so the first word came about 0.4 s later than step 6144 alone.
- `0023-lend-refill-behind.patch`: the lent cache (0022) comes back behind the writing instead of before it. With `LLAMA_MOE_CACHE_LEND_BEHIND=K` (1 to 4096; off unless set, and only with 0022's knob), the first short write after a lent read allocates the cache again and starts uploading its experts on a second stream of the same card, in a thread, while Bob goes on writing without the cache (as with no cache at all); at the K-th written token the engine waits for the upload if it isn't done yet and uses the cache again from the next token. K is a fixed count, not "when the upload is done", so the words don't depend on how fast the copy was: the same K gives the same words every time. A long read that comes while the upload runs waits for it first. If the card can't give a second stream the log says so and the cache comes back the 0022 way. The log says how long the upload took and how long the writing had to wait for it (`waited ... ms for the refill`). Expected on the PC: the first word as early as step 6144's, with the cache's writing speed from token K on (0.28 s of upload is about 25 words at the no-cache speed, so K about 24). - `0024-cache-read-layout.patch`: during a long read, the hot-experts cache holds whole layers instead of the hottest experts. - `0025-kq-mask-from-positions.patch`: the attention mask made on the card from positions instead of copied over as a big table. Every reading step, stock llama.cpp fills a table on the processor saying which earlier words each new word may look at (one 2-byte value per cache cell per word in the step), keeps it in pinned RAM and copies it to the card: at 256K with a 4096 step that is 2 GB of pinned RAM and a 2 GB copy for every step (Calibrate measured the `CUDA_Host compute` buffer growing by exactly that). With `LLAMA_KQ_MASK_BUILD=1` (off unless set) the engine sends only each cell's position and chat (4 bytes a cell, 1 MB at 256K) and each new word's position, and the card builds the same table from them in blocks of rows with stock operations (subtract, step, log, set rows), so a value is 0 or minus infinity exactly as the processor would write it. Covered: one chat or several (one cache or one per chat), flash attention on (f16) and off (f32), standard sliding windows (GPT-OSS, Gemma), holes in the cache (prompt-cache reuse), context shift, copied chats, draft words (MTP, speculative), the fused cell lists (`fused_kv_rows`). Not covered, so they keep the stock table, chosen per step: vision brains' 2-D positions, ALiBi brains, chunked or symmetric windows, non-causal attention, and a step where one stream mixes chats. Nothing that reads the mask changes: flash attention, the plain softmax path, and the CUDA tile-skip scan get the same table. Saves the pinned RAM and the copy (and the processor's fill); the card still holds the table, plus up to about 200 MB of working blocks at 256K (the true no-table version needs our own CUDA kernels, see ENGINE-MAP). Checked here (`engine/tests/mask-made.py`, two tiny made-up brains, one with a sliding window, 32 combinations): the odds are identical bit for bit, about 11 to 28 million values per combination. **Not run on a card yet.**
- `0026-kq-mask-positions-no-table.patch`: no attention mask table at all, not even on the card. (1) MTP replay (0130, `LLAMA_RS_REPLAY=1`): Vulkan already runs the replay form of the gated delta net, so this adds only its tests. (2) The 3-bit and 2-bit chat memory (0038 `q3_0`, 0046 `q2_kv`): writing (SET_ROWS, CPY), reading back (CPY, GET_ROWS) and flash attention straight from those types; the 2-bit writer picks its scale with the same rounding as the processor, so the stored bytes match. (3) Flash attention that also hands back each row's log-sum-exp (0045), which Progressive Memory (0039) and the sharp start (0122) merge with: the scalar and coopmat1 paths and the split-k reduce, with or without sinks; the back-end door (0045) now lets Vulkan say yes to it. (4) A quantized chat memory copied to 16-bit (0039's reading overlay), for every Vulkan cache type. The release zips now carry our Vulkan library (`ggml-vulkan.dll`, `libggml-vulkan.so`) and `lamplight-vulkan.json`, which tells Bob what it can do; Bob leaves both out over the CUDA download. Changes ggml-vulkan, one line of ggml-backend, and tests. Lossless where the matching CUDA path is (the same stored bytes and math); the features stay behind the same switches as on CUDA. Tested on the software Vulkan driver (lavapipe): `test-backend-ops` and `tests/vulkan-replay.py`. On a real AMD, Intel or NVIDIA card: unproven in our lab, as we have yet to test. Needs 0130 (it tests its op) and goes on with or without 0123-0125.
- `0136-nariq-trellis.patch`: loads and runs NariQ brains (Nari Labs' trellis-coded GGUFs, types TRL1-6, `nari-labs/nari-llama.cpp` branch `nariq/b12431`, MIT; its CUDA library libtrellis is Apache-2.0, both licence notices kept in the patch). Each 16x16 block of weights is a short circular bit stream; each weight is rebuilt from a 16-bit window of it with a multiply and four 6-bit digits, then the layer's Hadamard sides and scales are applied around the product. Nari's loader, converter side (`conversion/trellis.py`), CPU reference, CUDA (libtrellis, sm_80+) and Metal code come in as published, with these changes: (1) the type ids are 46-51 here, because 44 and 45 are our `q3_0` and `q2_kv`; `gguf.cpp` reads a file's 44-49 as TRL1-6 only when it carries `trellis.version`, and writes them back as 44-49, so files stay compatible; (2) the card-sharing wire numbers for the two new ops are 103 and 104; (3) left out: Nari's general CUDA fusions (add+rmsnorm, softplus, bf16 flash attention, narrow get_rows) and its in-place Qwen 3.5 state change, which overlap our own (0130 replay); (4) our own fast processor product (AVX-512 with VBMI, AVX2, ARM NEON): decode in registers, int16 inputs, decode-once for many tokens; (5) our own Vulkan kernels (decode GEMV for short batches, decode to f16 plus Vulkan's own matrix multiply for long ones, the sides in shared memory); (6) our own CUDA kernels for cards libtrellis can't run (below sm_80: RTX 20, GTX 16) and shapes it refuses, with cuBLAS for long batches (`LAMPLIGHT_TRELLIS_CUDA=own` uses them on every card, for comparisons). Keys, all for testing only: `LAMPLIGHT_TRELLIS_CPU=nari|exact|b16`, `LAMPLIGHT_TRELLIS_VK_MM_MIN`, `LAMPLIGHT_TRELLIS_CUDA_MM_MIN`. Normal GGUFs are untouched. Tested: `test-trellis` and `test-trellis-metadata` pass on the processor (AVX-512, AVX2, and ARM under an emulator) and on Vulkan (lavapipe, all 162 product cases); CUDA compiles here (sm_75 and sm_86) but has not run on a card. Speed on this cloud processor (4 cores, one 5120 x 17408 layer, 3 bits, one token): Nari's loop 18.3 ms, ours 3.4 ms with AVX-512 and 6.9 ms with AVX2, against 1.5 ms for Q3_K; 512 tokens: 188 ms with AVX-512 and 421 ms with AVX2, against 125 ms and 216 ms for Q3_K on the same two builds. On a real card: unproven in our lab, as we have yet to test.

Most patches change only llama.dll / libllama and llama-server. 0017, 0020, 0026, 0038, 0039, 0040, 0042, 0044, 0045, 0046, 0057, 0100, 0101, 0109, 0126, 0127, 0128, 0130, 0131, 0133, 0135 and 0136 also change ggml (see ENGINE-MAP.md), and then the build ships its own ggml files. Apart from those, `0004`, `0005`, `0006`, `0008` and `0011` change the card-sharing backend (`ggml-rpc.dll` / `libggml-rpc.so`), which is not a card backend and ships in the Brain Engine download. So a Windows Brain Engine is the official CUDA or Vulkan zip for the same tag with `llama.dll`, `llama-server.exe` and the other `llama*`/`mtmd` files swapped for the ones built here. It also carries two tools the official zips leave out (upstream skips them when the card backends load at run time), each built CPU-only as one self-contained file:

- `llama-cvector-generator`: the Lab's "Take out the refusal habit".
- `llama-export-lora`: the Lab's teach step, to fold a taught adapter into a brain file.

And four tools Bob runs beside the server, built from the same tag in the main build (they use the llama files above):

- `llama-bench`: the standard speed test (the Lab's Challenges, "Add the standard speed test").
- `llama-gguf-split`: joins a brain that comes in parts into one file (the Lab's "Bring in a full-size brain"), and splits one for an upload over Hugging Face's 50 GB limit.
- `ggml-rpc-server`: Bob-Net's "Lend my graphics card", so one brain can spread over several of your Bobs' cards. Bob starts it only when a paired Bob asks through the passcode door, binds it to 127.0.0.1 behind a gate that lets in only the asking Bob's address (on the home network when both are on it, else on this machine's Tailscale address; never 0.0.0.0), and stops it when that Bob lets go, after 3 minutes with no word, or when Gaming starts. The RPC server has no passcode of its own, which is why it is never left open.
- `llama-diffusion-cli`: runs diffusion brains (Dream, LLaDA, RND1) in the Lab's Playground. The official llama.cpp downloads don't have it (their builds leave the examples out), so it needs `-DLLAMA_BUILD_EXAMPLES=ON`.

The build turns on `-DGGML_RPC=ON` so the card server exists. Its `ggml-rpc` backend file is Brain Engine's own (patch 0004). Its `ggml-vulkan` file is Lamplight's own too (patch 0135), with `lamplight-vulkan.json` beside it; Bob puts both over the official Vulkan download and leaves them out over the CUDA one. When our `ggml-cuda` ships (on Windows, and on Linux from the Linux CUDA build), Bob leaves it out over any download that isn't the CUDA one, which has no CUDA runtime beside it. The other ggml files are never swapped.

The **Brain Engine** workflow (`.github/workflows/brain-engine.yml`) builds them when `engine/` changes on main or in a pull request that is ready for review, and by hand. Pushes to work branches and draft pull requests build nothing, so a patch that is still being worked on never sends a failed-build e-mail. Check a new or changed patch with your own build first: `bash engine/try-newer.sh` for a move to a newer tag, or apply the patches to a clone of the tag and build the same targets as the workflow (on Windows too when the patch touches code that includes `windows.h`).

## The Linux build

From Nov 26 the Linux files are built inside Ubuntu 22.04 (`engine/linux-build.sh`, run by the Brain Engine workflow in an `ubuntu:22.04` container), so nothing in the download needs a glibc newer than 2.35: Ubuntu 22.04 and 24.04, Debian 12 and their kin can run it. Built on the runner's own newer Ubuntu, Brain Engine 43 to 46 needed glibc 2.43, and llama-server would not start on those. The Pack step fails the build if any file needs more than 2.35. When a patch changes the CUDA backend, the download also carries our own `libggml-cuda.so`, built from the same patched tree with the CUDA version of the official Ubuntu CUDA download (as Windows carries `ggml-cuda.dll`); it goes over a copy of that official download, whose CUDA runtime stays beside it. To rebuild only the Linux file of a published test build, start the workflow by hand with `linux_release` set to its release (and `linux_without` for any later patch numbers on the branch).

## Moving to a newer llama.cpp

`engine/try-newer.sh [TAG]` puts the patches on the tag Bob is on now (one commit each), then replays them on `TAG` (default: the newest `bNNNN`) with git's three-way merge, so a patch whose surrounding lines only moved still goes on. The moved patches land in `try-newer/patches/` with the same names. When one needs a hand, `try-newer/conflict.txt` names it and its files.

Then: copy the moved patches into `engine/patches/`, set `bundledLlamaTag` in `package.json` to the new tag, add one to `bob.brainEngineVersion`, and push. The Brain Engine workflow builds it on Windows and Linux. Publishing the pre-release (`brain-engine-<brainEngineVersion>b<llama.cpp build>`, by hand with "publish" ticked), the PC test, and a Bob release that sets `bob.brainEngine` (tag and both sha256 prints) come after, so Bob's built-in llama.cpp and Brain Engine always move together.

**Version numbers.** Brain Engine has its own: every new build (new patches, or a newer llama.cpp underneath) gets the next `bob.brainEngineVersion`. From build 5 a build is named **N1bN2**: that number, a `b`, then the llama.cpp build it's made on, so build 5 on llama.cpp b12282 is **Brain Engine 5b12282**, its release `brain-engine-5b12282` and its files `brain-engine-5b12282-win-x64.zip` and `-linux-x64.tar.gz` (the workflow makes the name from `brainEngineVersion` and `bundledLlamaTag`). Always add one to `brainEngineVersion` before publishing, so a rebuild never replaces files a released Bob is pinned to. Older builds keep their names: 3 and 4 are `brain-engine-v3`/`brain-engine-v4` ("version 4, built on llama.cpp b12282"), and builds 1 and 2 are named after their llama.cpp tag (`brain-engine-b12032`, `brain-engine-b12282`). Bob reads all three (`public/engine-name.js`). Settings, Engines and the logbook name the build from the installed folder's marker, and when a brain loads Bob checks the running engine's `/props` `build_info` against the llama.cpp number in the name, and notes it in the logbook if they differ.

The **Brain Engine newer llama.cpp check** (`.github/workflows/brain-engine-newer.yml`) runs this every Monday and builds the result on Linux. When the patches go on and it builds, it opens one issue, "New Brain Engine ready on llama.cpp bNNNN - rebuild it?", with the moved patches as a download; later weeks edit that same issue. It never changes Bob, and the run stays green whatever it finds.

llama.cpp changes its card-sharing protocol now and then (b12359, llama.cpp 1.0, is version 10; b12282 was 9 and b12032 was 8), usually because it renumbers its list of math steps. From Brain Engine 8, patch 0014 keeps one frozen numbering on the wire (protocol 9's, the one Brain Engine 7 speaks) and HELLO says 9, so Brain Engine 7 and every later build share cards both ways. When llama.cpp adds a step, add it at the end of `bob_wire_ops` in that patch; when it drops one, put -1 in its place (the build fails until every step has a number). A Brain Engine 6 or older (protocol 8) still can't share with these.
