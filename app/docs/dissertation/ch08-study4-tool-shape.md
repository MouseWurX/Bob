# Chapter 8. Study 4: tool shape or lesson content

## 8.1 Introduction and research question

Bob gives a local model about 55 tools: files, office documents, pictures, diagrams, reminders, a notice board, web search, apps and more. A small model that misses a tool call can be at fault in two ways. The tools may be written badly, in their wording and their shape. Or the model may not have been taught what the tools are for, which is a fault in its lessons. The two causes call for different repairs, and the second repair is expensive: it means writing and training on new lessons.

This chapter answers research question 4: does tool shape or lesson content matter more for tool use? We use "wording" for the text of a tool's name, description and argument notes. We use "shape" for the tool set itself: which tools exist, how they split the work, what arguments they take and where their output goes.

The study ran on 13 to 15 November 2026 on three models. Bobert (35Bob) is the full Qwen3.6-35B-A3B trained on Bob's lessons. Riker (28Bob) is the same family cut to 208 of 256 experts and healed. GPT-OSS 120B is a different family and serves as a contrast. A fourth model, a 38B cut of GPT-OSS that was not healed, appears in the coaching tests only. Chapter 9 explains the cuts.

The short answer is that rewording the tools did not help, thinking did not help, and showing the exact correct call did. The misses cluster around tool shape. From these results MouseWurX locked one working tool shape per brain family on 15 November: shape 4 for Qwen brains and shape 3 for GPT-OSS brains (section 8.10). Every later lesson, tool test and call format in this dissertation is held to those shapes. The locked shapes were built from the coached runs but have not been re-scored as a whole, and this chapter says so wherever it matters.

## 8.2 Related work

**Tool use as a learned skill.** Toolformer (Schick et al., 2023) showed that a model can learn, from its own sampled data, when to call an API such as a calculator or a search engine and how to use the result. Gorilla (Patil et al., 2023) fine-tuned a model to write API calls and paired it with a document retriever so that it could follow changing documentation. ToolLLM and its ToolBench data (Qin et al., 2023) built an instruction set over more than 16,000 real-world APIs, with the data generated by a stronger model. All three treat tool use as something taught through data. Bob's own lessons follow that line, with a larger teacher model writing the lessons.

**Evaluating tool calls.** The Berkeley Function Calling Leaderboard (Patil et al., 2025) tests whether a model calls the right function with the right arguments, and extends to multi-step agent settings. It reports that top models handle single calls well but still struggle with memory, dynamic decisions and long-horizon reasoning. Our grading is stricter and narrower. A call counts as right only if it uses the same tools as the teacher's recorded answer with every recorded argument matching. That measures agreement with a teacher, not whether the user's goal was met (section 8.12).

**Tool descriptions.** Hsieh et al. (2023) found that written tool documentation can teach a model to use a tool without demonstrations, and can match few-shot examples. This predicts that tool wording should matter. We tested that prediction and found no effect on the models we studied. The difference may be that their tools were new to the model, while Bob's tools had already been taught in lessons (section 8.11).

**Sensitivity to wording.** Sclar et al. (2023) showed that small changes in prompt format can swing few-shot accuracy widely, and argued for reporting a range of performance across plausible formats. Our wording tests are a small case of the same idea. We report every variant with a paired gap and a 95% range, and we call a change real only when it exceeds that range.

**Acting with reasoning, and overthinking.** ReAct (Yao et al., 2022) interleaves reasoning steps with actions, and chain-of-thought prompting (Wei et al., 2022) showed that written intermediate steps help on multi-step problems. Against that, Chen et al. (2024) showed that reasoning models spend large amounts of compute on easy problems without gains in accuracy, which they call overthinking. Qwen3 (Yang et al., 2025) puts a thinking mode and a direct mode in one model, with a switch between them. The gpt-oss model card (OpenAI, 2025) describes models tuned for tool use and agent tasks, with a reasoning level that can be chosen. Our thinking-on and thinking-off comparison uses these switches on tool steps.

**How open agents shape tools for each model.** On 13 November we read the tool code of eleven open agent apps from their main branches (source only; nothing was run). The ones that adapt to a model change the tool's shape to the format that model was trained on, never its wording alone. OpenHands gives GPT-5 an `apply_patch` tool and Gemini the Gemini CLI tools. Cline sends GPT and Codex models to `apply_patch`. Aider picks an edit format per model from its own benchmarks. Open Interpreter emulates the harness each model's maker ships. Codex gives gpt-oss `shell`, `apply_patch` and `update_plan`. Several keep the plan as a tool the model updates (Codex `update_plan`, OpenHands `task_tracker`, Qwen Code `todo_write`), and several make finishing a checked step (Cline, Roo Code, smolagents `final_answer`). Their core tool sets are small: about 4 tools in OpenHands, 9 in Cline and 3 in Codex, against 16 core tools in Bob. This is a reading of design choices, not a measured result, and none of the plan, finish or small-set ideas has been A/B tested in Bob. It is unproven in our lab, as we have yet to test, whether they would help Bob's brains.

**What this study adds.** Published work mostly asks how to train or evaluate tool use. We ask a narrower, practical question about a fixed set of 55 tools and three small local models: where should the next unit of effort go, into the tool text, into the thinking setting or into the lessons?

## 8.3 Method

### 8.3.1 Subjects and settings

| Model | What it is | Engine and card | Slots |
|---|---|---|---|
| Bobert (35Bob) | Qwen3.6-35B-A3B trained on all of Bob's lessons, Q4_K_M | Brain Engine, rented 48 GB A40 | 8 slots of 8,192 tokens |
| Riker (28Bob) | Qwen3.6-35B-A3B cut to 208 of 256 experts per layer and healed, Q4_K_M | Brain Engine, rented 48 GB A40 | 4 slots of 16K tokens (after a first set-up with 8 slots of 8,192 failed) |
| GPT-OSS 120B | OpenAI model, native weights, thinking on and off | Rented card, lab bench | Not recorded in the lab files |
| GPT-OSS 38B cut | REAP cut of GPT-OSS 120B, not healed | Lab bench | Not recorded in the lab files |

Sources: bobert-35bob-tool-study.md, riker-28bob-tool-interview.md, the gptoss-tools WORDING.md and COACH.md files. The tool list and system prompt were Bob 1.5.223's. Tools were offered and parsed but never run. Tool results came from each lesson's own saved results.

### 8.3.2 Questions

The questions were 308 lesson turns across 14 jobs (apps, diagram, documents, files, knowledge, memory, office, pictures, plans, reminders, run, schedules, science and web). They were the first two assistant turns of each lesson. They came from held-out and reserved calibration lessons, never from training lessons. In every wording condition, 264 turns were judged for Bobert and for GPT-OSS 120B. Riker's wording table also reports 308 lessons per version for thinking off and 264 scored turns for the thinking-on per-job table.

Chapter 7 reports that many held-out items also appeared in training-side files. The tool-study turns come from held-out and calibration lessons, so the same caution applies here. We did not check these specific turns for leaks. This matters less for a comparison between conditions on the same turns than for an absolute score, but it is a limit.

### 8.3.3 Grading and noise

A turn was "right" when the model made the same tool calls as the teacher's recorded answer, with every recorded argument matching. "Tool right" counted the right tools with any arguments. The teacher was full Qwen3.6, so the grade measures agreement with the teacher, not truth. Gaps between conditions are paired differences on the same turns, with a 95% range. A gap is called real only when it is larger than its range.

### 8.3.4 The tests

1. **Wording and shape A/B.** The same turns were asked with variants of the tool text. The variants were: Bob's own wording; short "Use when" lines; a save path (`save_to`) on the five save tools; "act" (a prompt telling the model to call now, not ask, and never claim an uncalled step); forward-slash paths; one worked turn shape as an example; "fewer" (ask_specialist and mcp_tools hidden); parallel tool calls on; and combinations.
2. **Thinking on and off.** Each model's own thinking switch, on every tool turn. For Bobert we also tried a forced head start, "Plan: 1.", written at the start of the thinking.
3. **Coaching.** Real lesson steps were walked one at a time. After a wrong try the coach gave up to three hints: a nudge, the tool name, and then the exact call. The session then moved on along the lesson's own right path, so every step was judged from a correct state. Wrong calls were never run.
4. **Wish test.** The same jobs with no tools offered, to see which tool names and arguments the model invents.
5. **Self-interview.** The model was shown its own failed steps and asked why it erred and how the tool should be written.

The wish test and the self-interview are used here only as leads. Section 8.8 explains why.

## 8.4 Results: wording and shape

### 8.4.1 Rewording moved nothing beyond the noise

On GPT-OSS 120B, 264 turns, thinking off, Bob's own wording scored 0.633 (lab-PC WORDING.md for gptoss-120b). The other wordings were all within about one point:

| Condition (GPT-OSS 120B, thinking off, n 264) | Right | Right tool | Gap vs Bob's wording |
|---|---|---|---|
| Bob's wording | 0.633 | 0.777 | none |
| "Use when" lines | 0.621 | 0.758 | -0.011 +/- 0.032 |
| Save paths | 0.633 | 0.777 | +0.000 +/- 0.028 |
| "Use when" + save paths | 0.636 | 0.777 | +0.004 +/- 0.032 |
| "Use when" + paths + fewer | 0.625 | 0.769 | -0.008 +/- 0.032 |

Bobert showed the same pattern. His ten conditions are below (264 judged turns each, thinking off; bobert-35bob-tool-study.md):

| Condition | Right | Gap vs Bob's wording |
|---|---|---|
| Bob's own wording | 0.591 | none |
| "Use when" lines | 0.587 | -0.004 +/- 0.031 |
| Save paths on five save tools | 0.576 | -0.015 +/- 0.023 |
| "Act": call now, don't ask | 0.591 | +0.000 +/- 0.028 |
| Forward-slash paths | 0.591 | +0.000 +/- 0.026 |
| One worked example | 0.572 | -0.019 +/- 0.027 |
| "Fewer": ask_specialist and mcp_tools hidden | 0.610 | +0.019 +/- 0.031 |
| Parallel tool calls on | 0.583 | -0.008 +/- 0.028 |
| Act + parallel + fewer + slash | 0.587 | -0.008 +/- 0.035 |
| All parts combined | 0.576 | -0.019 +/- 0.029 |

No change beat Bob's wording beyond the noise. "Fewer" led, but its gap is inside its range. Bobert's per-job moves were small samples and none was clearly real. Examples were files (0.684 with "Use when" against 0.526), run (0.500 for the four-part combination against 0.313) and apps (0.636 against 0.364).

Riker, thinking off, scored 178 of 308 with Bob's wording and 174, 175 and 175 with the three alternatives (riker-28bob-tool-interview.md, section 3.1). All four are within the noise.

One result stood out. With thinking on, Riker's file jobs rose from 0.368 to 0.579 when "Use when" lines and save paths were added (+0.211 +/- 0.188). It is one of only two per-job gaps in the study that clear their range; the other is a fall, GPT-OSS 120B's plans job with thinking on (section 8.5). Overall, the same change moved Riker from 0.538 to 0.580 (+0.042 +/- 0.042), which sits at the edge of the noise. When a user named a file, Riker used the save path in 2 of 3 turns with the new wording, against 0 of 3 with Bob's. That is three turns, so it is a lead, not a finding.

### 8.4.2 Per-job wording on GPT-OSS 120B

The per-job table for GPT-OSS 120B (n per job in brackets) shows how much per-job gaps wander when samples are small. With "Use when" lines, apps rose by 0.182 +/- 0.239 (n 11) and run by 0.188 +/- 0.198 (n 16). Science fell by 0.167 +/- 0.177 (n 18) and web by 0.086 +/- 0.094 (n 35). None clears its range. Knowledge, the largest group (n 48), did not move at all: 0.875 under three of the four wordings.

Web is the weakest job in all conditions: 0.457 for Bob's wording, with a right-tool rate of 0.714. In that job the model picks the right tool far more often than it gets the arguments to match the teacher, which is the pattern the grading is least able to separate from legitimate variation in search words (section 8.12).

### 8.4.3 Aggregating the wording tests

Across three models and many conditions, none of the wording changes produced a reliable gain. The best candidate for a real effect is Riker's file jobs with thinking on. It fits the models' own explanations: Riker's self-interview and the earlier GPT-OSS interview both blamed tools that make a file without saying where it goes (section 8.8). The shape change in section 8.9.1 acts on exactly this point.

## 8.5 Results: thinking on and off

| Model | Thinking off | Thinking on | Note |
|---|---|---|---|
| GPT-OSS 120B | 0.633 | 0.542 | 9.1 points worse (+/- 5.0); the thinking-on cells were trimmed by MouseWurX |
| Bobert | 0.591 | 0.545 | right tool 0.727 against 0.708 |
| Bobert, all wording parts, thinking on | | 0.564 | right tool 0.723 |
| Bobert, all wording parts, thinking on, head start "Plan: 1." | | 0.403 | n 159; right tool 0.604 |
| Riker, Bob's wording | 178 of 308 | 161 (52%) | |
| Riker, "Use when" + paths | 175 of 308 | 172 (56%) | |

Thinking did not improve the first tool call. The forced head start clearly hurt Bobert. Riker with thinking on ran out of length 18 times against none with thinking off, and needed the third hint more often (26 times against 17, section 8.6). Bobert showed one exception on small samples: apps with the act and parallel prompt and thinking on scored 0.909 against 0.636, and thinking fixed open_app against app_look there. It is one job at n 11.

The GPT-OSS per-job table shows where thinking hurt most: plans fell by 0.250 +/- 0.195 (n 20), files by 0.158 +/- 0.271, science by 0.167 +/- 0.238 and office by 0.111 +/- 0.121. Two figures clear their range: plans (-0.250 +/- 0.195, n 20) and the overall figure (-0.091 +/- 0.050) (WORDING.md).

The GPT-OSS interview study ran a separate test on whether a short written thinking style, or a pre-filled head start, changes how the model thinks (gpt-oss-120b-tool-interview.md, section 3.4). With Bob's full prompt and tool list present, style adherence was 0.00 to 0.05 out of 1 in every variant. Without tools and with a short prompt, adherence was 0.55 to 0.63. The model's reasoning voice reverts to its default once the tool list is present. This is a small study (five requests per variant), but it agrees with the main result: prompting does not steer thinking on tool turns.

These results hold for the three models and the grading used. They say that, for these brains, tool steps do better with thinking off. They do not say that thinking is useless on planning or review turns, which this study did not test. Section 8.9.2 covers the change made from this.

## 8.6 Results: coaching and hint ladders

### 8.6.1 The ladders

Coaching ran on 83 lesson steps for Bobert and Riker (up to four steps of each lesson the model had missed with Bob's wording, at most three lessons per job). GPT-OSS 120B ran on 83 steps and the 38B cut on 81, thinking off only (MouseWurX's call on 15 November). Each cell below is the number of steps solved at that stage.

| Model, thinking | First try | After hint 1 (nudge) | After hint 2 (tool) | After hint 3 (exact call) | Never | Solved with hints |
|---|---|---|---|---|---|---|
| Bobert, off | 40 | 10 | 8 | 15 | 10 | 73 of 83 (88%) |
| Bobert, on | 41 | 3 | 9 | 18 | 12 | 71 of 83 (86%) |
| Riker, off | 41 | 10 | 10 | 17 | 5 | 78 of 83 |
| Riker, on | 38 | 6 | 6 | 26 | 7 | 76 of 83 |
| GPT-OSS 120B, off | 45 | 10 | 6 | 7 | 15 | 68 of 83 (computed from the cells) |
| GPT-OSS 38B cut, off | 32 | 11 | 5 | 10 | 23 | 58 of 81 (computed; 4 errors) |

Sources: bobert-35bob-tool-study.md section 4; riker-28bob-tool-interview.md section 3.2; the gptoss-tools COACH.md files. The sum for each row is its step count. The "solved with hints" column for the last two rows is our addition from the cells.

Four readings follow.

1. **The exact call teaches.** For Bobert, hint 3 solved 15 steps with thinking off and 18 with it on, more than either earlier hint. For Riker it solved 17 and 26. A bare nudge almost never helped Bobert with thinking on: it fixed 3 of 42 misses.
2. **Nudges help a little with thinking off,** and not at all with thinking on. A model that spends its length on its own reasoning makes less use of a short hint.
3. **The cut GPT-OSS model starts well behind its parent.** It got 32 of 81 right first time against 45 of 83, and never solved 23 against 15. It had four errors, and no heal had been run on it. This is the same pattern chapter 9 reports for cuts in the Qwen family.
4. **Riker's first-try figures understate him.** The step checker was strict on free-text inputs such as search words and picture prompts, and a reasonable search with different words counted as wrong. The loose regrade has not been done.

Coaching leaks the answer by design. "Solved with hints" therefore measures teachability, not first-try skill.

### 8.6.2 Where the ladder fails

Bobert's hardest jobs were run, science, web, plans and diagram. In diagram, 2 of 4 steps were never solved with thinking off. For GPT-OSS 120B the hardest were web (1 of 7 right first time, 4 never) and files (3 of 8, 4 never). Its easiest was memory (4 of 4). For the 38B cut, web scored 0 of 6 on the first try, and pictures scored 2 of 8 with 5 never solved.

The coaching files record what the model called first at each step where a given tool was wanted. "(words)" means the model answered in text with no call.

**Bobert** (thinking off, then on; bobert-35bob-tool-study.md section 4):

|---|---|

| Tool wanted | What it called first (count) |
|---|---|
| list_folder | search_files 12, (words) 8, notice_board 1 |

Counts are per step and small. We read the pattern, not the numbers.

**What recurs.** Four habits repeat across the models and across wordings.

- **Near-twin tools.** ask_specialist, pick_session, use_tools and offer_setup pull Bobert off course. He skips loader tools and goes straight to the real tool.
- **open_app versus app_look.** Bobert, Riker and GPT-OSS 120B all sometimes use app_look, or offer_setup, when open_app was wanted.
- **write_file through the shell.** Bobert and the 38B cut both reached for run_command where write_file was the file-writing tool.
- **Folder jobs.** GPT-OSS 120B answered in words 16 times and used search_files 5 times where list_folder was wanted. The 38B cut used search_files 12 times and answered in words 8 times. Riker made long chains of list_folder calls. The folder job is the one most confused with its neighbour.

These are faults of design and of lessons together. Rewording did not fix them. Showing the exact call did.

The earlier GPT-OSS interview (gpt-oss-120b-tool-interview.md) traced 303 rejected lessons it had written. The largest model-side fault was not verifying a tool's result and then misreporting it (62 rows). A further 50 rows were caused mainly by unrealistic simulated tool results, and 86 of 303 (28%) were caused or made worse by them. Twelve rows were traced to a tool description that misled it. The tool group where the notice board failed (43 rejected, 2 kept) was fixed in PR #219 by changing the notice board's wording to add and done actions. That interview is about writing lessons, not answering them, but it supports the same point: much of what looks like a model fault is the tool's shape or the test set-up.

## 8.8 Leads only: the wish test and the self-interview

Two tests asked the model to talk about itself or to act without tools. We treat both as leads, not results.

### 8.8.1 The wish test

With no tools offered, Riker was given the same 116 jobs and any tool call he wrote in text was recorded (riker-28bob-tool-interview.md, section 3.3).

| Measure | Thinking off | Thinking on |
|---|---|---|
| Jobs where he wrote a tool call | 74 of 116 | 43 of 116 |
| Calls that would have worked (Bob's exact tool or a clear synonym) | 38 (33%): 23 exact, 15 synonyms | 29 (25%) |
| Hand-checked sample | 7 of 10 workable | |

His own names for tools included run_program (for run_command), fetch_page (for web_search) and read_dir (for list_folder). His most common invented argument names were `name`, `prompt`, `action`, `command`, `description`, `content`, `path` and `url`. He invented make_tool where office_make was wanted, and wrote raw shell commands instead of using Bob's file tools.

The lead is that a model reaches for plain names and plain argument names, so aliases and plain argument names may cost less than retraining. The test was not planned for that run: a lost PC session meant the old test ran in place of the coach, and its results were kept as evidence. It was run once, on one model, with one grader on workable calls.

### 8.8.2 The self-interview

Riker was shown 10 of his failed steps and nine tool groups, and was asked why he erred and how each tool should be rewritten. GPT-OSS 120B had an earlier interview of eight failures and 14 tool groups.

The models' answers were specific. Riker's STRUGGLES lines named missing save paths, an unclear working folder, ambiguous `reference` values in the picture tools and undefined defaults. GPT-OSS 120B's proposed rewrites almost always added an output path or name, explicit defaults, conditional required fields or a returned saved path.

Against that, the GPT-OSS 120B interview found its predictions about itself were poor: it named its weak spot correctly in 3 of 13 scorable groups, and it did not foresee its two largest real failure areas, the notice board and folder listing. Six group requests got no answer because of network errors. In the feedback round the model read our "fail / kept" counts backwards, so its accuracy claims there are void.

The lead is that models explain a single failure plausibly when shown their own trace, and that their explanations point the same way as an independent trace analysis. The limit is that a model's account of its own error is a plausible story, not proof of its cause. We compared the explanations with saved thinking and calls for that reason.

## 8.9 Shape changes built in PR #251 and PR #271, and thinking per step in PR #253

### 8.9.1 PR #251: tool shapes version 2

The results above point to shape, not words. PR #251 built the changes. Its commit message in release 1.5.238 lists:

- a `save_to` argument on make_image, make_sound, save_as and make_diagram, and a new name for convert_file;
- `~` and bare names accepted in the Hands tools;
- reminders cancelled by words, not only by id;
- tool-name aliases that map the names models invent onto Bob's tools;
- app_look opening the app first;
- the tool-shape stamp raised to 2, which makes the tool record start a fresh history and archive the old one.

These map to the observed misses: file-making tools without a path, short paths, cancelling a reminder by its text, invented tool names, and app_look used for open_app. An earlier draft of this chapter said the GPT-OSS shape was built in the same pull request. It was not: release 1.5.238 shipped PR #251 only up to shape 2, and the GPT-OSS shape was locked later, in PR #271 (section 8.9.3).

**This is not re-tested.** No run has measured whether tool shape v2 raises any score. PR #251 shipped in release 1.5.238, whose pre-release check passed 276 of 276 test suites (1.5.238-PC-CHECKS.md), but a test suite passing says nothing about tool accuracy. The test of the claim in this chapter is a rerun of the wording and coaching tests on shape v2 with the same turns.

### 8.9.2 PR #253: thinking per step

PR #253 is recorded in the commit message for release 1.5.239. It adds a switch, on by default, with the setting name `stepThinking` and the label "Think to plan and review, not on each step". It also makes GPT-OSS thinking off send a low reasoning effort, and adds an effort option to the Lab's tool tests.

This is a direct use of section 8.5. It follows the result that thinking hurt tool steps but is not known to hurt planning or review. We have not measured its effect on any score, on any model. It is a design response to one study, and the study cannot validate it.

They are the evidence the shapes were built from, not tests of the shapes.

## 8.10 Findings on agent tool shapes

This section gathers what the project now holds about tool shapes, with the evidence for each. Findings 1 to 4 rest on measurements in this chapter. Findings 5 to 8 are rules MouseWurX set from them, and they bind the rest of the dissertation.

1. **Wording is not the lever.** No rewording beat Bob's own wording beyond the noise on any of the three models (section 8.4; GPT-OSS 120B 0.633, every variant within 0.03; Bobert 0.591, every variant within 0.02; Riker 178 of 308 against 174 to 175). This agrees with the open agents of section 8.2, which change shape per model and never wording alone.
2. **Shape is where misses recur.** The misses that repeat across models are near-twin tools, open_app against app_look, file writing through the shell and folder listing (section 8.7). Each is a fault of which tools exist and how they divide the work, not of their text.
3. **Build the tool the way the brain reaches for it.** A habit a brain shows consistently, in 2 of 3 tries and in both thinking modes, becomes the tool's shape, and a one-hint fix stays a wording fix. This is MouseWurX's rule of 14 November. With Bob's tools offered, Riker never invented a tool name in coaching and always reached for Bob's own (riker-28bob-tool-interview.md); only with no tools offered, in the wish test, did he write plain names of his own (section 8.8.1). So Qwen keeps Bob's names. GPT-OSS also stayed inside Bob's function names in coaching (section 8.7), although its earlier interview spoke of using a browser tool (finding 8).
4. **Thinking belongs to planning and review, not to tool steps.** Thinking lowered GPT-OSS 120B from 0.633 to 0.542 (-0.091 +/- 0.050), and a forced head start lowered Bobert to 0.403 (section 8.5). Tool steps therefore think off for Qwen and low for GPT-OSS. Whether thinking helps planning and review turns is unproven in our lab, as we have yet to test.
5. **One working shape per family: Qwen shape 4, GPT-OSS shape 3** (section 8.9.3). Every family gets the same tool names and inputs, so a call runs the same way whichever brain wrote it. A family's set differs only by leaving out the tools that pulled it off course and by one-line notes on a pair it confuses. A family's whole list is never longer than Bob's own (test/run-tool-sets-test.js).
6. **Lessons follow their family's shape, and never cross families.** Qwen brains learn only Qwen-shaped lessons and GPT-OSS brains only GPT-OSS-shaped ones. Every lesson carries `family` and `tool_shapes` stamps (model-lab/write-lessons.mjs), the pre-flight refuses a Bob tree of the wrong shape (`--want-shapes`), and the heal skips a lesson stamped for another family (model-lab/forge/pod/data.py). Lessons and tool tests use only the newest locked shape; results on an older tool list are reported as such and are not compared with shape-4 results as if they were the same test.
7. **The call format follows the working shapes.** MouseWurX's rule of 16 November is that the tool-call format must adhere to the tool shapes that work. A stricter call format, such as one that constrains the brain's output, may only hold the brain to the exact names, inputs and order in the tool list Bob sends. It may not change the shape. It stays off until it passes a check against shapes 3 and 4. No such format has been built or tested.
8. **Native GPT-OSS tools wait on the engine.** The open agents give gpt-oss its maker's own tools (browser, python, apply_patch), and our reading of the engine found that upstream llama.cpp's GPT-OSS parser reads only `to=functions.NAME` calls and drops `to=browser.*` calls (Bob's own text-call reader, src/llamacpp.js, matches only `functions` as well). Bob's GPT-OSS shape therefore stays in the functions namespace with Bob's names. Whether native tools would beat shape 3 is unproven in our lab, as we have yet to test.

What remains open is the measured effect of the locked shapes themselves. The test is the shape-4 rerun above, with the same rerun for GPT-OSS on shape 3.

## 8.11 Discussion

**What the three results add up to.** Wording is not the lever, thinking is not the lever, and the exact call is. Both the Riker and Bobert write-ups conclude that coached seeds should show the full right call, and that lessons showing the full correct call should help more than "use tool X" hints. This is the claim that tool-use lessons need to carry the shape, which supports the thesis of this dissertation. The lesson content that teaches an exact call comes from the lesson set, and chapter 6 reports that the set holds many faults.

**Shape or content?** The study does not separate the two. A near-twin tool is a fault of shape, because two tools overlap. The model's habit of calling the wrong twin is a fault of lessons, because lessons taught it what to call. A change to the shape alone, such as removing ask_specialist and mcp_tools ("fewer"), gave the highest score for Bobert (0.610 against 0.591) but not beyond the noise. The honest answer to research question 4 is therefore:

1. rewording the text of existing tools does not matter on the three models tested;
2. thinking on does not help tool steps on any of them;
3. what recovers a miss is seeing the exact call, which is a lesson, and the misses that recur are those where two tools overlap, which is shape;
4. whether shape changes alone raise scores is untested. The shapes were locked from the coaching evidence (Qwen shape 4, GPT-OSS shape 3; section 8.10), and the shape-4 rerun is the test.

**Why does this differ from the documentation result?** Hsieh et al. (2023) found that documentation could teach new tools. Bob's tools were already in the lessons the models had seen. A model that has been trained on a tool's calls may weight those calls above its description. We did not test a tool the model had never seen, and this is a possible reading, not a finding.

**Link to the rest of the thesis.** A hidden fault in the lessons can look like a tool-shape problem. The models' misses and the lesson faults overlap: lessons that finish with a pretend result, or that pick the wrong twin tool, will teach exactly the habits in section 8.7. The interviews also showed that 28% of GPT-OSS's rejected lessons were tied to unrealistic simulated results. The lesson-side check of how many tool lessons are clean is in chapters 6 and 11: Opus read all 5,788 non-held-out tool lessons and kept 189 as they stand, fixed 1,381, repaired 4,208 and discarded 10 (checked numbers file). The decisive test, a retrain on reviewed lessons followed by a re-run of this study, has not been run.

## 8.12 Threats to validity and limits

- **Grading measures agreement with the teacher,** not ground truth. A reasonable call with other words counts as wrong, especially in free-text arguments. Riker's coached first-try numbers were most affected.
- **Bobert's slot size.** His engine served 8 slots of 8,192 tokens each. The planned switch to 4 slots of 16K never happened. 11 to 13 long turns per round overflowed the slot, and 11 to 31 answers per round were cut off at the length limit. All were scored wrong. They were the same knowledge, office, plans, science and web turns each round, so the comparison between conditions stays fair, but absolute scores are low. Time to first token was not logged.
- **Riker's set-up faults.** The first set-up used 8 slots of 8,192 tokens, so 24 of 616 prompts could not be sent and every thinking-on answer was cut off. The coached lessons were run by hand after a PC session dropped. A first pass at 12 experts per word was invalid because a steering push stayed on. Ten thinking-on answers per version were still cut off at 16K. Each problem now has a check (riker-28bob-tool-interview.md section 5).
- **Slot settings differ across models,** so the three models are not directly comparable on absolute score.
- **One run per condition.** Per-job cells have 4 to 48 turns. Treat per-job numbers as signals.
- **Multiple comparisons.** Across ten conditions and 14 jobs, some per-job gaps will clear their range by chance. We called only gaps larger than their range real. Two per-job gaps clear their range: Riker's file jobs with thinking on (19 turns) and GPT-OSS 120B's plans job with thinking on (20 turns). Either could be chance.
- **Thinking-on cells for GPT-OSS 120B were trimmed** by MouseWurX (option C in the WORDING.md header), so its thinking-on coverage is smaller than its thinking-off coverage.
- **Different graders, different dates.** The earlier GPT-OSS interview used Bob 1.5.108 tool text and the later tests 1.5.223.
- **Coaching is not a test of skill.** It leaks the answer by design.
- **The wish test and self-interview are leads,** as set out in section 8.8.
- **Experts per word.** Bobert at 12 experts per word scored 0.595 (tool 0.739), level with his own 8. The all-parts combination at 12 scored 0.557 (-0.038 +/- 0.036), borderline worse. Riker's 12 experts per word scored 175 of 308 against 178 at 8. An earlier Riker result of 68% against 65% on held-out chats (MAKING-SMALLER-MODELS.md) did not repeat in this study.
- **Held-out leaks.** The source turns come from lesson files whose held-out items may overlap training files (chapter 7). We did not check this set.
- **Cost.** Bobert's share of the shared card was about 3.7 hours and about US $2.17, with two earlier pods that never started costing about $0.37, total about $2.54. Riker's sessions cost about $5.82 on 14 November.

## 8.13 Summary and still to do

For three small tool-using models, rewording the tools did not raise accuracy beyond the noise, thinking on lowered it, and the exact correct call recovered most misses. Hint ladders reached 88% (Bobert), 78 of 83 (Riker) and, by our sum, 68 of 83 for GPT-OSS 120B and 58 of 81 for its unhealed 38B cut. The misses repeat in the same places: near-twin tools, open_app against app_look, file writing through the shell and folder listing. These are faults of shape and of lessons together.

Shape changes were built (PR #251), a thinking-per-step switch was built (PR #253), and one working shape per family was locked (PR #271): shape 4 for Qwen brains and shape 3 for GPT-OSS brains. Lessons, tool tests and any stricter call format now follow those shapes (section 8.10). None of these changes has been re-scored.

Still to do:

1. Re-test Qwen shape 4 (Riker, then Bobert) and GPT-OSS shape 3 on the same turns (model-lab/forge/plans/shape4-retest.json; its first try froze at start-up).
2. Regrade Riker's coached steps loosely.
3. Rerun Bobert at 4 slots of 16K.
4. Test whether lessons that show the full call beat lessons that describe it, ideally with the same lessons run through the review described in chapter 11.
5. Measure thinking per step on a score, not on design alone.
6. Test GPT-OSS's native tools against shape 3 once the engine can read them (section 8.10, finding 8).
